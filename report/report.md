# SMS Spam Detection

**Студент:** Gleb Sanin  
**Задача:** определить по тексту SMS, является ли сообщение спамом.  
**Код и деплой:** FastAPI + Streamlit, запуск локальный.

## 1. Постановка задачи

Я решал обычную для антиспам-фильтра задачу: на вход приходит короткое SMS-сообщение, на выходе нужен класс `ham` или `spam`. В таком сценарии важна не только общая доля правильных ответов. Если модель почти всегда говорит `ham`, accuracy может быть приличной, но пользы от такого фильтра мало.

Поэтому основной метрикой я использовал `F1` для класса `spam`. Она держит в фокусе баланс между двумя ошибками: пропущенным спамом и ложной блокировкой нормального сообщения. В таблицах также оставлены `precision`, `recall` и `accuracy`, чтобы было видно, за счёт чего меняется F1.

## 2. Данные

Источник - SMS Spam Collection, открытый корпус сообщений для задачи spam filtering. Он доступен в UCI и на Kaggle:  
https://www.kaggle.com/datasets/uciml/sms-spam-collection-dataset

После очистки осталось 5 158 уникальных сообщений.

| Класс | Количество |
|---|---:|
| ham | 4 516 |
| spam | 642 |

Датасет меньше формального порога в 10 000 строк, но он был согласован для проекта. В сыром файле фактически две полезные колонки: метка и текст. Для текстовой классификации это не критично: TF-IDF превращает поле `message` в набор n-грамм, а часть поведения спама дополнительно описывается ручными признаками.

## 3. Подготовка данных

Код подготовки лежит в `src/data.py` и `src/features.py`.

Что делает пайплайн:

- читает исходный архив `sms_spam_collection.zip`;
- приводит метки к единому виду и кодирует `ham = 0`, `spam = 1`;
- удаляет пустые сообщения и точные дубли;
- добавляет признаки по тексту сообщения;
- сохраняет обработанный датасет локально в `data/processed/`.

Ручные признаки простые и интерпретируемые: длина сообщения, число слов, количество цифр, доля uppercase, пунктуация, наличие URL, телефона, валютных символов и CTA-слов вроде `call`, `free`, `claim`, `win`.

Разбиение данных стратифицированное: `70/15/15` на train, validation и test. Векторизаторы находятся внутри sklearn pipeline, поэтому словарь и IDF считаются только по train-части. Так validation и test не подмешиваются в обучение.

Из EDA видно три вещи:

- классы несбалансированы, spam заметно меньше;
- spam чаще содержит цифры, телефоны, денежные маркеры и призывы к действию;
- длина сообщения помогает, но не является самостоятельным решением задачи.

## 4. Baseline

В качестве baseline использовалась связка `CountVectorizer + MultinomialNB`. Это быстрый и понятный вариант для текстовой классификации без ручных признаков.

| Модель | Accuracy | Precision spam | Recall spam | F1 spam |
|---|---:|---:|---:|---:|
| CountVectorizer + MultinomialNB | 0.979 | 0.966 | 0.866 | 0.913 |

Baseline оказался сильным, потому что часть спама в корпусе довольно шаблонная: встречаются слова `free`, `call`, `claim`, короткие номера, суммы и обещания выигрыша.

## 5. Эксперименты

Я сравнивал простые текстовые модели и вариант с ручными признаками. Основная гипотеза была такая: для коротких SMS линейные модели на n-граммах должны работать хорошо, а признаки вроде телефона, валюты и CTA-слов помогут на пограничных примерах.

| Гипотеза | Как проверялось | Результат |
|---|---|---|
| Bag-of-words даст сильный baseline | `CountVectorizer + MultinomialNB` | `F1_spam = 0.913` на test |
| TF-IDF будет устойчивее CountVectorizer | `TF-IDF + LogisticRegression` | `F1_spam = 0.819`, recall стал ниже |
| Линейная SVM лучше разделит n-граммы | `TF-IDF + LinearSVC` | `F1_spam = 0.951` на validation |
| Ручные признаки добавят сигнал к тексту | `TF-IDF + manual features + LogisticRegression` | `F1_spam = 0.928` на test |

Итоговые метрики:

| Модель | Split | Accuracy | Precision spam | Recall spam | F1 spam |
|---|---:|---:|---:|---:|---:|
| CountVectorizer + MultinomialNB | test | 0.979 | 0.966 | 0.866 | 0.913 |
| TF-IDF + LogisticRegression | test | 0.961 | 0.986 | 0.701 | 0.819 |
| TF-IDF + LinearSVC | val | 0.988 | 1.000 | 0.906 | 0.951 |
| TF-IDF + LinearSVC | test | 0.978 | 0.955 | 0.866 | 0.908 |
| TF-IDF + manual features + LogisticRegression | test | 0.983 | 1.000 | 0.866 | 0.928 |

## 6. Финальная модель

Для локального сервиса выбрана `TF-IDF + ручные признаки + LogisticRegression`. `LinearSVC` был сильнее на validation, но для интерфейса логистическая регрессия удобнее: она возвращает вероятность spam-класса через `predict_proba`. Это значение показывается в API и Streamlit как `spam_score`.

Интерпретация ожидаемая:

- слова и n-граммы вроде `free`, `call`, `claim`, `prize`, `urgent` двигают предсказание в сторону spam;
- телефоны, валютные символы и CTA-слова усиливают этот сигнал;
- короткие бытовые сообщения без ссылок, цифр и призывов к действию чаще остаются в классе `ham`.

## 7. Деплой

Для CP3 сделаны два локальных интерфейса.

FastAPI:

- `GET /health` - простая проверка, что сервис жив;
- `POST /predict` - предсказание по JSON с полем `message`.

Пример запроса:

```json
{
  "message": "URGENT! You won a free prize. Call now to claim cash."
}
```

Пример ответа:

```json
{
  "label": "spam",
  "target": 1,
  "spam_score": 0.9902
}
```

Streamlit:

- поле для ввода SMS;
- кнопка проверки;
- вывод класса и `spam_score`;
- два встроенных примера: обычное сообщение и сообщение, похожее на спам.

Скриншоты лежат в `report/images/`:

- `api_predict_example.png`;
- `streamlit_interface_example.png`.

Видео демонстрации: https://disk.yandex.ru/i/pJhz8z5Rq__DAw

Команды запуска:

```bash
uvicorn app.api:app --host 127.0.0.1 --port 8000
streamlit run app/streamlit_app.py --server.address 127.0.0.1 --server.port 8501
```

## 8. Выводы

Проект доведён до состояния, в котором его можно запустить локально и проверить на своих SMS. API подходит для программного вызова модели, Streamlit - для ручной проверки одного сообщения.

Главное ограничение - сам датасет: он небольшой и не новый. Для реального антиспам-фильтра следующим шагом был бы сбор более свежих сообщений, проверка качества на новых данных и подбор порога `spam_score` под допустимый уровень ложных срабатываний.
